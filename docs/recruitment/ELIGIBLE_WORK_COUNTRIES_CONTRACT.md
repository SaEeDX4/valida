## 1. The four concepts, kept apart

| Concept | Where it lives | What it may establish |
| --- | --- | --- |
| Physical job location | `Job.location` (Doc 10 §§24–28); public `location` text | Where the role is based or advertised. **Never** eligibility |
| International recruitment audience | Not a field (OD-2026-11-09-01 R1) | Nothing about eligibility |
| Regional presentation | The frontend selector (`markets.js`, 21 countries) and the optional, frontend-only `hiringMarkets` | How location and pay are presented in a regional view. **Never** eligibility |
| **Eligible remote-work countries** | **`Job.eligibleWorkCountries`** | The countries from which Valida has approved an employee to perform that remote role — **only** as listed explicitly for that vacancy |

Nothing derives the fourth from the others, from NOC 21220 (`internalOccupationalReference`), from a publication country or from nationality.

## 2. The representation

- **Type.** An array of strings: **ISO 3166-1 alpha-2 codes**, uppercase exactly as written, in display order, each at most once.
  - Example: `["NZ", "DE"]`.
  - Maximum length: the number of assigned codes (249).
- **Code set.** `backend/src/modules/jobs/countryCodes.js` (accepted codes) and `frontend/src/features/jobs/countryNames.js` (English names).
  - Both are generated by `backend/scripts/generate-country-tables.mjs` from one input: Debian iso-codes 4.16.0 `iso_3166-1.json`, SHA-256 `f01b812b…c89f`.
  - The name is iso-codes `common_name`, or `name` otherwise.
  - A test checks that both tables have exactly the same codes, and that the 21 selector labels equal the table names.
- **Refused everywhere** (definition schema, model, DTO mapper, frontend contract):
  - lowercase or padded codes, unassigned codes (`XX`), alpha-3 codes, names;
  - duplicates;
  - non-strings and non-lists;
  - a non-empty list on a `HYBRID` or `ON_SITE` Job.
- **Absent and empty** both mean that no country is approved. No country is named, and no eligibility is claimed.

## 3. Behaviour by layer

| Layer | Behaviour | Code |
| --- | --- | --- |
| **Model** (Doc 10) | `eligibleWorkCountries: [String]`, default `[]`, validated on every save. A Job stored before the field existed loads as `[]` and stays valid. Not part of publish readiness | `backend/src/models/Job.js`; rules in `backend/src/modules/jobs/eligibleWorkCountries.js` |
| **Edit allowlist** | Editable as a whole list through `applyJobEdit` | `job.service.js` `EDITABLE_FIELDS` |
| **Controlled provisioning** (Doc 12 §§46–47; Doc 15 §§171–175) | The **only optional content key** of a definition. **Omitted:** the stored list is kept (a new Job gets none). **`[]`:** a deliberate clear. **List:** exactly those codes. **Invalid input** is refused before the database is contacted (definition schema), or before any write (plan refusal `ELIGIBLE_WORK_COUNTRIES_INVALID`, for a kept list on a Job the definition makes hybrid). The stored record is unchanged either way. The field is **material** (`MATERIAL_FIELDS`, Doc 12 §41). The CLI prints where the list comes from (`from the definition` / `not in the definition: the stored list is kept`) and the stored list | `job.provisioning.js`, `scripts/provision-job.mjs` |
| **Public API** (Doc 09 §63) | `GET /api/v1/jobs/:jobSlug` adds `eligibleWorkCountries`, always present (`[]` when none), after `compensation`. `GET /api/v1/jobs` (list) is **unchanged**. A stored list that is not valid fails closed: a safe 500, never a narrowed or widened list | `job.mapper.js`, `job.repository.js` `DETAIL_PROJECTION` |
| **Frontend contract** | `isUsableJobDetail` accepts an absent list (an older response) and a valid one; a malformed list makes the response malformed (error state; 503 from the document server) | `features/jobs/api/jobContract.js` |
| **Visible content** (Doc 06 §§97–98) | A **fully remote** Job with a non-empty list shows **"Eligible Remote-Work Countries"** with the country names, in order, joined with ", ". The row sits in Employment Details, after Compensation. It is shown on open and retained closed pages, and is independent of the regional selector. No row otherwise | `features/jobs/utils/eligibleWorkCountries.js`, `pages/JobDetailPage.jsx`, `JobDetailPage.content.js` |
| **JobPosting** (Doc 16 §§124–138) | **Open, fully remote, with a non-empty list:** the JobPosting adds `jobLocationType: "TELECOMMUTE"` and `applicantLocationRequirements` (one `{ "@type": "Country", "name": … }` per code, same names and order as the row). The description repeats the visible "Work Arrangement" and "Eligible Remote-Work Countries" rows. **Remote without a list:** the whole JobPosting is withheld (`NO_APPLICANT_ELIGIBILITY`), in the initial HTML and the rendered page. Hybrid or on-site: withheld (`NO_STRUCTURED_WORKPLACE`). Closed: withheld. Navigation away removes it | `seo/jobPosting.js` (shared by the browser and `frontend/server/`) |
| **Careers and Apply** | Unchanged. The list row and the Apply context do not carry the field | — |

## 4. The genuine vacancy

`backend/provisioning/jobs/cybersecurity-specialist.json` stays a **DRAFT**:
- `eligibleWorkCountries: []`;
- both `location` and `eligibleWorkCountries` are in `awaitingInput`, so publication is refused (`AWAITING_INPUT`), and each one alone is enough;
- "British Columbia, Canada / CA / BC" is kept as the **historical planning value of the physical work location**, with its provenance in the notes. It is not an eligible work country.

**The minimum remaining decision** is the explicit list of countries from which Valida has confirmed it can employ someone to perform this role.

## 6. How authorised administrators will manage it (Release E — not implemented)

Until E3, the operating method is controlled provisioning (§3): an operator edits the vacancy's definition file and runs `plan`, then `apply`. That is data, not a code change per advertisement.

At **E3 — Job management** (Doc 18 §§230–234), the same field is maintained per vacancy through the approved lifecycle, with no new role or permission:

| Lifecycle step | Clause | Permission (Doc 11 §§150–152) | The field |
| --- | --- | --- | --- |
| Create Draft | Doc 12 §§19, 213 | `jobs:create` | May be set or left empty |
| Edit | Doc 12 §§21, 40, 214 | `jobs:update` | A country multi-select over the **ISO list** (not the 21-country selector). The same validation as §2. A change is material when Applications exist (Doc 12 §§41–42) |
| Draft preview | Doc 12 §§22–23 | Admin session | Shows the row exactly as the public page will |
| Publish / reopen | Doc 12 §§25, 34–36, 215, 217 | `jobs:publish` | Readiness unchanged. A remote Job without a list publishes with no JobPosting |
| Close / archive | Doc 12 §§29–39 | `jobs:close`, `jobs:archive` | No effect on the list |
| Audit | Doc 12 §§208–210 | `audit:read` | A change is a `JOB_UPDATED` event, with the changed field named in safe metadata |

The Admin API contract and form are designed and approved at E3. Nothing here implements them.
