## 2. Key rules (Doc 11, Doc 12)

**Accounts and tokens**
- No public signup and no default password.
- The first owner comes from the `npm run admin:provision` CLI. Later Admins are invited by an owner and receive a one-time emailed activation link (32 random bytes, 8 hours, token in the URL fragment).

**Passwords**
- Argon2id via Node's built-in implementation; m=19456, t=2, p=1; PHC encoding; rehash on login.
- 12–128 characters, local common-password check, never truncated.
- Unknown emails go through a dummy verification, so timing does not reveal accounts.

**MFA**
- Mandatory TOTP (RFC 6238, ±1 step, replay refused).
- Secret encrypted with AES-256-GCM under a server key named by key id.
- 10 one-time recovery codes of about 128 bits each, stored as hashes.
- Owner-run MFA reset after out-of-band identity verification; audited.

**Sessions** (`express-session` + `connect-mongo`)
- Cookie: `__Host-valida.sid`, Secure, HttpOnly, SameSite=Strict, host-only.
- Regenerated at the password step and at the MFA step.
- 30-minute idle and 8-hour absolute limits, enforced on the server.
- `authVersion` revocation; session list and revocation.

**Request protection**
- Synchronizer CSRF token.
- Origin / Referer / Sec-Fetch-Site checks.
- Credentialed CORS for the Admin origin only.

**Abuse limits**
- 30 login attempts per 15 minutes per client address.
- 5 consecutive failures lock the account for 15 minutes.
- 5 wrong codes end the MFA challenge.

**Password reset**
- 30 minutes, single use; revokes every session; keeps MFA; no automatic sign-in; generic response.

**Step-up**
- High-risk actions need strong authentication in the last 10 minutes.

**Roles**
- `ADMIN_OWNER` has all 17 permissions.
- `RECRUITMENT_ADMIN` has recruitment permissions only: no `admins:*`, no `audit:read`.
- Default deny; last-owner protection.

**E4: search and storage keys**
- Search is built on the server from plain text; browser input never becomes a query operator or regex.
- The storage key is never returned to the browser.

**E4: résumé release**
- Released **only** when the scan status is `CLEAN`.
- The audit event `RESUME_ACCESSED` is written **before** any byte is sent.
- Sent as an attachment with `nosniff` and `private, no-store`.

**E5: stale updates**
- A status change names the status it replaces. A stale or concurrent change is refused (`STATUS_CONFLICT`).

## 4. Production configuration it needs (for the later, separately authorised deployment)

1. **API environment:**
   - `ADMIN_AUTH=enabled`
   - `ADMIN_SESSION_SECRET` (32+ random bytes, base64url)
   - `ADMIN_MFA_KEYS=<id>:<base64 32 bytes>` and `ADMIN_MFA_CURRENT_KEY_ID=<id>`
   - `ADMIN_APP_ORIGIN`: `https://app.cybervalida.com` while private, then `https://cybervalida.com` at public activation
   - Keep `TRUST_PROXY=2` on Render. The API must sit on the **same site** as the frontend (`api.cybervalida.com`) for the `SameSite=Strict` session cookie to travel. `*.onrender.com` hosts are cross-site, because `onrender.com` is a public suffix
2. **Atlas — database permissions** (corrected 2026-11-22, PR #3; the source of truth is `backend/src/ops/backup/mongoRoles.js`)
